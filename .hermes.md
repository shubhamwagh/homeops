# .hermes.md — HomeOps project context

Project-specific operating context for Hermes in the `shubhamwagh/homeops` GitOps repo.
Source of truth for **persistent cluster configuration** is this Git repository; live state is
reconciled by Flux. This file is documentation only — it carries no secrets, no transient
cluster state, and no personal profile (that lives in `USER.md` / `SOUL.md`).

## Purpose
HomeOps is a bare-metal **k3s** homelab (3 nodes) managed entirely via GitOps. It is both
useful personal infrastructure and a learning environment. Hermes is deployed into it as a
GitOps-managed, namespace-scoped operator with high autonomy for ordinary apps and no critical
privileges by default.

## Source-of-Truth Model
```
live state → diagnose → locate owning HomeOps manifest → modify Git → validate
→ commit/push when authorised → Flux reconciles → verify live state
```
Direct Kubernetes mutation is for runtime recovery / restarts / ephemeral stabilisation only.
Do not leave permanent drift: a persistent change belongs in Git, not in an imperative `kubectl`
edit. (Note: when Git write is later enabled, the path Hermes → Git → Flux → K8s means **Flux**
is the API caller, a separate trust boundary from Hermes' own SA — record this fact.)

## Cluster Topology (durable)
- 3-node k3s cluster, LAN `192.168.0.0/24`. node1 = control-plane + subnet router; node2/node3 = workers.
- Names: `homelab-hpg2-node1/2/3` (verified live). node1 is `Ready,control-plane,etcd`.
- k3s version `v1.35.x` (k3s1). Cilium CNI with L2 load-balancer announcing VIP `192.168.0.2`.
- Do not treat the node currently hosting Hermes' Pod as special — it is scheduled normally and
  may move.

## Flux Reconciliation Flow (verified from `clusters/staging/`)
GitHub `homeops` → Flux `GitRepository/flux-system` → Kustomizations (all in `flux-system` ns):
```
infrastructure        path: infrastructure/staging   wait:true
  └─ infrastructure-config   path: infrastructure/config/staging   dependsOn: infrastructure
        └─ apps                path: apps/staging                   dependsOn: infrastructure, infrastructure-config
```
All three use `decryption: sops` via the `sops-age` Secret. Key implication: if `apps` are
unhealthy because `infrastructure-config` is not Ready, investigate **upstream**, not each app
independently. `infrastructure` uses `wait:true` so HelmReleases (CRDs) settle before config
CRDs and apps reconcile.

## Repository Structure (where to make a change)
- `clusters/staging/` — Flux entrypoint Kustomizations + `flux-system` (gotk components, managed by `flux bootstrap`).
- `infrastructure/base/<area>/` — platform HelmReleases / manifests: `networking` (cilium, traefik, cert-manager, cloudflared, headscale, headplane), `storage` (longhorn + recurring-jobs), `monitoring` (kube-prometheus-stack, metrics-server), `controllers` (reloader, renovate, reflector, cnpg), `security` (crowdsec, vaultwarden), `searxng`.
- `infrastructure/config/base` + `/staging` — CRD-dependent config: cert-manager ClusterIssuers + wildcard cert, Traefik Middleware, postgres (CNPG) cluster/namespace.
- `infrastructure/metal/` — Ansible inventory + playbooks (gitignored generated config; provisions k3s over SSH via k3sup).
- `apps/base/<app>/` — one dir per application (namespace, deployment/statefulset, service, ingress, pvc, configmap, `*.sops.yaml`). Staging overlays at `apps/staging` and `infrastructure/staging` just reference `../base`.
- `apps/base/hermes-agent/` — Hermes' own deployment, RBAC, admission policy, break-glass templates.
- `vps/headscale/` — encrypted (SOPS) Ansible inventory/group_vars for the Oracle VPS running Headscale.
- `.sops.yaml` — age **public** recipient only (no private key). `secrets-manifest.yaml` — pointers classifying HUMAN-ACCESS vs MACHINE-ONLY (no values). `renovate.json`, `Makefile`, `mise.toml`, `.github/workflows/ci.yml`.

Pattern: add a new ordinary app under `apps/base/<app>/` **and** add a matching
`hermes-operator-write` RoleBinding entry (see Hermes Authority) before Hermes can operate it.

## Application Conventions
Apps are mostly raw Kustomize manifests (not Helm) under `apps/base/<app>/`: namespace,
Deployment/StatefulSet, Service, Ingress (Traefik IngressRoute/Middleware in `infra/config` for
shared TLS), PVC (Longhorn), ConfigMap, and `*.sops.yaml` Secrets. Bases hold desired state;
`apps/staging` / `infrastructure/staging` are thin overlays. Platform pieces (Cilium, Traefik,
cert-manager, Longhorn, monitoring, CNPG, Renovate, Reloader, Reflector, CrowdSec, Vaultwarden)
are Flux **HelmReleases** in `infrastructure/base/<area>` — each HelmRelease lives beside the
release it manages (not centralised in flux-system). Conventions differ between app manifests and
platform HelmReleases; don't assume a single universal pattern.

## Platform Components (verified present)
- **Networking:** Cilium (CNI + L2LB VIP `192.168.0.2`), Traefik (ingress, `*.shublab.com`),
  cert-manager (Let's Encrypt, Cloudflare DNS-01), cloudflared, Headscale (self-hosted Tailscale
  control plane on an Oracle VPS), Headplane (Headscale UI).
- **Storage:** Longhorn distributed block storage, `reclaimPolicy: Retain`; PVCs are RWO.
- **GitOps:** Flux v2 (`flux 2.9.x`), Kustomize, HelmRelease; source-controller pulls from GitHub.
- **Observability:** kube-prometheus-stack (Prometheus, Grafana, Alertmanager), metrics-server,
  kube-state-metrics, node-exporter.
- **Automation:** Renovate (daily PRs), Reloader, Reflector (syncs TLS Secret across namespaces), CI (GitHub Actions).
- **Database:** CNPG (CloudNativePG) PostgreSQL (`infrastructure/config/base/postgres`).
- **Security:** SOPS+age, CrowdSec, Hermes' own admission policy (below).

## Network / Exposure Path (actual)
```
client → DNS (Cloudflare *.shublab.com → 192.168.0.2) → Cilium L2LB VIP
→ Traefik (IngressRoute) → Service → Pod
```
Two access classes:
- **Public:** `*.shublab.com` via Cloudflare DNS-01 + Traefik ingress (TLS via cert-manager).
- **Private/tailnet:** Headscale VPN to `headscale.shublab.com` and internal `.shublab.com`
  services. `cloudflared` exists for tunnel use but is **not** assumed to be the primary public
  path (Cloudflare DNS-01 + Traefik is). Don't conflate "Cloudflare DNS exists" with "Cloudflare
  Tunnel is in use". LAN access is `192.168.0.0/24`.

## TLS / Certificate Model
- cert-manager with **two ClusterIssuers**: `letsencrypt-prod`, `letsencrypt-staging` (both Ready,
  verified live).
- **Wildcard** `*.shublab.com` certificate via Cloudflare DNS-01 challenge.
- **Reflector** copies the TLS Secret across namespaces (Traefik ingress + apps consume it).
- Documented durable caveat (from repo): this is a wildcard cert design; per-app certs would
  need their own Issuer/Request. No transient cert status stored here.

## Storage Model
- Longhorn is the storage backend; volumes are 3-replica by default (verified: 14 volumes live).
- Default StorageClass Longhorn, `reclaimPolicy: Retain` (deletion of a PVC does **not** free the
  underlying volume automatically — treat PVC/PV/Longhorn delete as RED/critical).
- **Replicas and snapshots are NOT an off-cluster backup.** Do not claim recovery readiness merely
  because a volume has replicas. Storage/data deletion always requires explicit approval.

## Secrets Model
- SOPS + age. All secrets committed as `*.sops.yaml`, decrypted by Flux via the `sops-age` k8s
  Secret. `.sops.yaml` holds only the age **public** recipient.
- `secrets-manifest.yaml` (not gitignored, no values) classifies each secret as **HUMAN-ACCESS**
  (a person logs in / basic-auth) vs **MACHINE-ONLY** (consumed by a pod), and **recoverable**
  (`sops -d` yields the literal value) vs **hash-only** (one-way htpasswd/bcrypt/apr1 — plaintext
  existed only at creation; `.secrets-plaintext` / Vaultwarden is the sole record for those).
- Local operator convenience (gitignored, generated): `make secrets-plaintext` (human-access dump),
  `make secret APP=<app>` (one app), `make secrets-plaintext-machine` (separate raw machine-only dump).
  These are caches, NOT the Git source of truth.
- **Hermes design:** encrypt-only. No age private key, no `get secrets` RBAC, no K8s Secret API
  access, no Vaultwarden access. Hermes may generate/encrypt new SOPS config via the public
  recipient but cannot decrypt. The admission policy (below) additionally blocks Hermes from
  introducing new Secret references into workloads.

## Hermes Authority (HomeOps-specific enforcement)
- **ServiceAccount:** `hermes-agent/hermes-homelab`. Deployed by `apps/base/hermes-agent` (the same
  repo it operates).
- **Observer (cluster-wide):** `hermes-operator-read` ClusterRole+Binding — get/list/watch across
  most resources (nodes, namespaces, events, pods/log, workloads, ingress, PVC/PV, Flux, Longhorn,
  Cilium, Traefik, cert-manager, metrics). **No secrets, no write verbs, no exec/attach/port-forward,
  no RBAC, no node/host.**
- **Ordinary operator (namespace-scoped):** `hermes-operator-write` ClusterRole, bound via
  RoleBindings **only** in these 8 namespaces (verified equal to my `can-i create deployments` set):
  `better-booking-bot, blog, car-health-check, hermes-agent, homepage, ntfy, tandoor, trek, uptime-kuma`.
  Covers: pods/delete (restart), services/configmaps CRUD, deployments/statefulsets/daemonsets CRUD
  (+scale), replicasets patch/delete, jobs/cronjobs CRUD, ingresses CRUD, HPA CRUD. **Not** secrets,
  PVC/PV, storage classes, namespaces, Longhorn, RBAC, CRDs, node/host, networkpolicies.
- **Flux reconcile (narrow, cross-namespace):** `hermes-operator-flux-reconcile` ClusterRole
  (`patch` on Kustomizations/HelmReleases only), bound in `flux-system` + each namespace holding a
  HelmRelease (cert-manager, cnpg-system, crowdsec, kube-system, longhorn-system, monitoring,
  reflector, reloader, renovate, traefik, vaultwarden). This is the one write that reaches protected
  platform namespaces — it only triggers reconcile-now / suspend / resume, nothing else.
- **Protected namespaces (read-only to Hermes):** `kube-system, flux-system, longhorn-system,
  cert-manager, traefik, cilium-secrets, monitoring, cnpg-system, crowdsec, vaultwarden, reloader,
  reflector, renovate, headscale, cloudflared, searxng, default`, etc. Mutation there is denied by RBAC.
- **Admission guardrail:** `ValidatingAdmissionPolicy hermes-secret-guard-workloads` +
  `...-cronjobs` (binding `hermes-secret-guard-workloads`, **validationActions: [Deny, Audit]**,
  enforced) — applies **only** to `hermes-homelab`. Blocks Hermes from creating/updating workloads that
  introduce a NEW/CHANGED secretKeyRef/secretRef/secret volume/imagePullSecret, change
  serviceAccountName, or set privileged / added-capabilities / hostPath / hostNetwork / hostPID /
  hostIPC. (Confirmed live via server-side dry-run: a `hostNetwork: true` Deployment in `blog` was
  denied by this policy.) Residual accepted risk: Hermes can still read an **already-referenced**
  Secret via `pods/log` in its 8 namespaces — which is why protected namespaces stay read-only.
- **Break-glass:** `hermes-critical-operator` ClusterRole + `serviceaccount-critical` exist but are
  **unbound by default**. `make hermes-elevate` (after explicit approval) binds them; `make
  hermes-revoke` removes them; `elevation-revoker` auto-revokes. Elevation is externally controlled
  by Shubham and adds RED-tier destructive capability **only** — never Secrets read, never
  exec/attach/port-forward, never node/host/SSH. **Hermes cannot self-elevate.**
- **Secret boundary:** `get/list secrets` cluster-wide = `no`. `secrets` API itself is forbidden to
  this SA. Critical elevation does not grant Secret access.

## Direct K8s vs GitOps Authority
Hermes may mutate directly (runtime): Pod delete/restart, rollout, ordinary application recovery,
limited app mutations in its 8 namespaces, and Flux `patch` (reconcile/suspend) in the listed
namespaces. **Durable desired-state changes belong in HomeOps Git.** Hermes-specific admission
policies govern direct API calls by `hermes-homelab`; the future Git-write path routes through Flux
instead, which is a distinct caller/trust boundary.

## Renovate / Release Model
`renovate.json` extends `config:recommended` (daily PRs; `renovate-github-token` in a SOPS secret).
Renovate proposes candidate updates; the future Release specialist must evaluate release notes,
compatibility, breaking changes, migrations, backup/rollback before important upgrades. Do not
blindly apply every Renovate PR.

## Diagnostic Hierarchy (normal app incident)
1. user-visible symptom → 2. workload status → 3. Pods/restarts → 4. events → 5. logs → 6.
Service/Endpoints → 7. Ingress/TLS/DNS → 8. PVC/storage → 9. metrics/resources → 10. Flux
desired-state/revision → 11. broader platform dependencies. **Do not restart first and investigate
later.** Trace upstream Flux dependencies before treating a downstream app as an independent failure.

## Flux Troubleshooting
Kustomization not Ready → check its `dependsOn` (infra before config before apps) and the source
revision. HelmRelease not Ready → chart pull / values / CRD readiness. Source failure → GitRepository
artifact / branch. Dependency failure → an upstream Kustomization/HelmRelease not Ready. Suspension →
`spec.suspend: true` (Hermes may toggle via flux-reconcile patch). Revision mismatch → local vs
remote commit differ (reconcile or investigate drift). Errors → `flux logs` / controller logs.

## Storage Troubleshooting
PVC Pending → StorageClass/Longhorn node/scheduling/quota. Volume degraded → replica health.
Attachment failure → node/csi. Disk capacity pressure → node filesystem (distinct from Longhorn
volume health). App I/O errors → mount/PV. **Storage/data deletion is RED/critical**; no destructive
recovery recipes here.

## Network Troubleshooting
Pod/app → Service → Endpoints (no healthy Endpoint ⇒ stop before DNS) → Ingress (Traefik
IngressRoute) → TLS/cert-manager → DNS (Cloudflare) → client/private (tailnet). Include Cilium /
network policy where relevant. Don't jump to external DNS if the Service has no Endpoint.
